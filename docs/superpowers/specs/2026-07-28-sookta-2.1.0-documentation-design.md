# Design Specification: Sookta Application 2.1.0 Documentation

วันที่อนุมัติโครงสร้าง: 28 กรกฎาคม 2026  
ภาษาเอกสาร: ภาษาไทยเป็นหลัก ใช้ภาษาอังกฤษเฉพาะชื่อมาตรฐาน โมเดล สูตร ตัวแปร และคีย์เวิร์ดที่จำเป็น

## 1. เป้าหมาย

จัดทำเอกสารสองรูปแบบจากหลักฐานชุดเดียวกัน โดยจัดทำตามลำดับดังนี้

1. เอกสารกลางแบบสมดุลสำหรับคณะวิจัยและทีมพัฒนา

ในไฟล์เดียว เอกสารแต่ละฉบับต้องส่งมอบทั้ง Word (`.docx`) และ Markdown
(`.md`) โดย Word และ Markdown ของเอกสารฉบับเดียวกันมีเนื้อหาสาระตรงกัน
รวมไฟล์ส่งมอบทั้งหมดสี่ไฟล์ และยังไม่จัดทำ PDF ในรอบนี้

## 3. หลักฐานและลำดับความน่าเชื่อถือ

เมื่อข้อมูลขัดแย้งกัน ให้ใช้ลำดับความน่าเชื่อถือต่อไปนี้

1. Source code ที่ทำงานอยู่ใน branch ปัจจุบัน
2. Model asset, schema และ metadata ที่บรรจุในแอป
3. Automated test และผล UAT ที่ตรวจพฤติกรรมจริง
4. Requirement ที่ผู้ใช้อนุมัติ
5. เอกสารภายใน repository
6. Guideline, มาตรฐาน และงานวิจัยจากแหล่งภายนอก

เอกสารต้องแยกให้เห็นชัดระหว่าง:

- วิธีมาตรฐานหรือแนวทางที่อ้างอิงจาก REBA/ISO
- การประยุกต์หรือ calibration เฉพาะของ Sookta
- โมเดลที่ผ่านการฝึกจากข้อมูลวิจัย
- coefficient/template ที่ยังรอ outcome label สำหรับฝึกใหม่
- legacy/deprecated component ที่ไม่ใช่ production path

ห้ามกล่าวอ้างว่า implementation เป็นไปตามมาตรฐาน ISO ทั้งฉบับ หาก source ใช้เพียงสูตรประยุกต์หรือ multiplier บางส่วน

## 4. ขอบเขตเอกสารกลางแบบสมดุล

### 4.1 ส่วนต้น

- ปกเอกสาร
- Document Control: release/document version, source snapshot version,
  branch, commit SHA และวันที่
- วัตถุประสงค์
- ขอบเขต
- กลุ่มผู้อ่าน
- คำเตือนว่าเป็นเครื่องมือสื่อสารความเสี่ยงทางการยศาสตร์ ไม่ใช่การวินิจฉัยโรคหรือใบรับรองทางการแพทย์
- สรุปผู้บริหาร

### 4.2 Flow การสร้าง Application

อธิบายตั้งแต่เริ่มต้นจนได้ไฟล์พร้อมเผยแพร่:

1. รวบรวมความต้องการและปัญหาจากภาคสนาม
2. วิเคราะห์ requirement และจัดลำดับความสำคัญ
3. ออกแบบ UX/UI, data model และ assessment pipeline
4. พัฒนา Flutter application และ on-device model integration
5. เพิ่ม local persistence, draft, history และ export
6. ทดสอบหน่วย ทดสอบ widget และทดสอบ regression
7. UAT บน iPhone และ Android จริง
8. ปรับ production configuration และ platform parity
9. กำหนด version/build และ signing
10. สร้าง IPA/AAB ตรวจ metadata และเตรียมส่ง Store

ต้องมีแผนภาพ Development Lifecycle หนึ่งภาพ และตารางหลักฐานที่เชื่อมโยงแต่ละระยะกับเอกสารหรือชุดทดสอบ

### 4.3 Workflow การทำงานของ Application

ต้องแยกเส้นทางอย่างชัดเจน:

- Application startup และ state restoration
- เข้าใช้งานครั้งแรก: Splash → เลือกภาษา → กรอกข้อมูล → เลือก Avatar → หน้าหลัก
- เข้าใช้งานครั้งต่อไป: Splash → Restore → หน้าหลัก
- กรณีมีภาษาแล้วแต่ setup ยังไม่เสร็จ
- การเลือกและจัดการเกษตรกรหลายคน
- การเลือกกิจกรรม
- การสร้าง บันทึกอัตโนมัติ กู้คืน และล้าง Draft
- การเลือกภาพ/วิดีโอและตรวจความพร้อม
- Pose estimation และการประเมิน
- Initial result → เลือกวิธีลดความเสี่ยง → Final result
- การบันทึกประวัติ ดูแนวโน้ม และ export
- เส้นทาง error/fallback ที่มีผลกับผู้ใช้

ต้องมีแผนภาพอย่างน้อยสี่ภาพ:

1. Application startup decision flow
2. First-run workflow
3. Returning-user workflow
4. Assessment end-to-end workflow

### 4.4 วิธีการคำนวณ

ต้องครอบคลุมการคำนวณที่ปรากฏใน production path และการคำนวณประกอบทั้งหมด:

1. BMI และเกณฑ์หมวดหมู่
2. Pose landmark confidence และการหา midpoint
3. มุมลำตัว คอ ต้นแขน แขนล่าง และเข่า
4. การแปลงมุมเป็น REBA component score
5. REBA Table A, B, C, load, coupling, activity และ safety floor ของ Sookta
6. การแปลง REBA เป็น user score 1–9 และ risk level
7. งานยก/ขนย้าย: reference mass, HM, VM, FM, DM, RWL และ LI
8. งานดัน/ดึง: initial-force ratio, sustained-force ratio และค่าที่สูงกว่า
9. การรวม REBA และ ISO ด้วยค่าความเสี่ยงและคะแนนที่สูงกว่า
10. ความเสี่ยงรายอวัยวะ
11. ค่าใช้จ่ายเฉลี่ย ค่าตัวคูณความเสี่ยง วันหยุดงาน และผลกระทบทางเศรษฐกิจ
12. การเปรียบเทียบก่อน/หลังและอัตราลดผลกระทบต่อคะแนน
13. การคำนวณแนวโน้ม ค่าเฉลี่ย ค่าสูงสุด slope และ feature normalization
14. Logistic Regression ของข้อมูลย้อนหลังเจ็ดรายการ
15. XGBoost/ONNX posture inference และ probability threshold
16. การสรุป frame ratio และเวลาเสี่ยงจากวิดีโอ
17. การเลือกคำแนะนำตาม risk level, body part และ activity

แต่ละหัวข้อต้องมี:

- วัตถุประสงค์
- input
- สูตรหรือ pseudocode
- หน่วย
- threshold
- output
- ตัวอย่างคำนวณอย่างน้อยหนึ่งตัวอย่างในสูตรสำคัญ
- ข้อจำกัด/assumption
- source mapping
- guideline/reference mapping

### 4.5 Guideline และแหล่งอ้างอิง

ใช้รูปแบบอ้างอิง APA 7 และให้ความสำคัญกับ primary/official source:

- REBA original paper
- ISO 11228-1, ISO 11228-2 และ ISO 11228-3
- ILO Ergonomic Checkpoints in Agriculture
- MoveNet official documentation/model information
- Logistic Regression และ XGBoost/ONNX ที่เกี่ยวข้องกับ implementation
- งานวิจัยหรือแหล่งข้อมูลต้นทางของ economic impact ถ้ามีหลักฐานในโครงการ

ต้องมีตาราง Traceability:

`หัวข้อในแอป → สูตร/พฤติกรรม → guideline → source file/method → test/evidence → หมายเหตุความสอดคล้อง`

### 4.6 ส่วนท้าย

- Data persistence และ privacy
- ข้อจำกัดทางวิชาการและข้อจำกัดของโมเดล
- Testing/UAT evidence
- คำศัพท์
- ตารางตัวแปร
- Source code index
- Bibliography

## 5. ขอบเขต Technical Specification

Technical Specification ใช้หลักฐานและสูตรเดียวกับเอกสารกลาง แต่เปลี่ยนระดับการนำเสนอเป็นเชิงระบบ:

1. System context และ architecture
2. Flutter module/package structure
3. Route map และ state transition
4. `SooktaAppState`, persistence key, schema version และ migration
5. Domain model และ serialization contract
6. Media ingestion, image storage และ video-frame extraction
7. Pose model, feature schema และ quality gate
8. Assessment pipeline และ production readiness gate
9. Algorithm specification ของ REBA, ISO และ combined result
10. Economic impact algorithm
11. Recommendation engine
12. Daily prediction และ ML asset contract
13. History, draft, export และ training-data schema
14. Error handling, telemetry และ fallback
15. Platform configuration ของ iOS/Android
16. Test architecture และ requirement-to-test matrix
17. Build, versioning, signing และ Store artifact verification
18. Source code reference index

สูตรทุกสูตรต้องมี method/class mapping และ pseudocode ที่สอดคล้องกับ source ปัจจุบัน

## 7. รูปแบบ Markdown

- ใช้หัวข้อแบบลำดับชั้นเดียวกับ Word
- ใช้ Mermaid สำหรับ flowchart และ architecture diagram
- ใช้ตารางเฉพาะข้อมูลที่ต้องเปรียบเทียบหรือ traceability
- สูตรใช้สัญลักษณ์ที่อ่านได้ใน Markdown พร้อมคำอธิบายตัวแปร
- ใช้ relative link ไปยัง source file และเอกสารภายใน repository
- ใช้ citation key ที่อ่านได้และมี Bibliography ท้ายเอกสาร

## 8. การสร้างแผนภาพใน Word

แผนภาพใน Markdown ใช้ Mermaid เป็น source of truth จากนั้น render เป็นภาพความละเอียดสูงสำหรับฝังใน Word โดยต้อง:

- ใช้คำภาษาไทยเป็นหลัก
- ไม่ให้ข้อความล้นหรือเล็กเกินไป
- มีคำบรรยายภาพและหมายเลขภาพ
- ระบุเส้นทาง success, validation failure, fallback และ data persistence เมื่อเกี่ยวข้อง
- ใช้สีตามความหมายอย่างสม่ำเสมอ

## 9. การตรวจสอบคุณภาพ

### 9.1 Content QA

- ไม่มี `TBD`, `TODO` หรือ placeholder
- ไม่มีข้อขัดแย้งระหว่างเอกสารสองฉบับ
- สูตรตรงกับ source และ test
- แยกมาตรฐาน การประยุกต์เฉพาะแอป และโมเดล template ชัดเจน
- ทุก claim เชิงมาตรฐานมี citation
- ทุก algorithm สำคัญมี source mapping
- ระบุข้อจำกัดของการประเมินจากภาพ 2D และข้อมูลที่ไม่ครบ
- ระบุว่า daily prediction coefficient ปัจจุบันยังไม่ใช่ research-trained coefficient หาก asset ยังคงสถานะดังกล่าว

### 9.2 Markdown QA

- Markdown lint ในระดับโครงสร้าง
- Link ภายใน repository ใช้งานได้
- Mermaid syntax ผ่าน
- heading hierarchy ไม่ข้ามระดับ
- ตารางไม่กว้างจนอ่านไม่ได้

### 9.3 Word QA

- ตรวจ font mapping ว่าใช้ Sarabun สำหรับ Latin และ Complex Script
- ตรวจ style, numbering, table geometry, heading และ page setup
- Render DOCX เป็น PNG ทุกหน้า
- ตรวจทุกหน้าที่ 100% zoom
- ไม่มีข้อความล้น ตารางขาด รูปแตก ตัวอักษรหาย หรือหน้าว่างผิดปกติ
- ตรวจความสอดคล้องกับ Markdown
- ไม่ส่งมอบไฟล์ PNG/PDF ที่ใช้ตรวจภายใน

## 10. ลำดับการดำเนินงาน

1. ตรวจ source และสร้าง evidence inventory
2. ตรวจ official guideline/reference
3. เขียน Markdown ของเอกสารกลาง
4. ตรวจสูตร source mapping และ citation
5. สร้าง Word เอกสารกลางด้วย Sarabun
6. Render และแก้ไขจนผ่าน visual QA
7. เขียน Markdown ของ Technical Specification จาก evidence ชุดเดียวกัน
8. ตรวจ cross-document consistency
9. สร้าง Word Technical Specification
10. Render และแก้ไขจนผ่าน visual QA
11. ส่งมอบ Word และ Markdown รวมสี่ไฟล์ พร้อมสรุปความแตกต่างของสองรูปแบบ

เอกสารทั้งสองฉบับใช้ evidence inventory ชุดเดียวกันเพื่อลดความขัดแย้ง แต่
ต้องสร้างสารบัญ ลำดับหัวข้อ คำอธิบาย และภาคผนวกของตนเองโดยสมบูรณ์

## 11. สิ่งที่ไม่อยู่ในขอบเขตรอบนี้

- ไม่แก้ไข application source code
- ไม่เปลี่ยนสูตรหรือ model asset
- ไม่สร้าง PDF
- ไม่ upload เอกสารไปยังระบบภายนอก
- ไม่กล่าวอ้างการรับรองมาตรฐานหรือการวินิจฉัยทางการแพทย์
