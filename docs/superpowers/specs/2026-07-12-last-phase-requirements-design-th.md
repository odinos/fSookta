## เป้าหมาย

ตรวจสอบ requirement ทุกข้อในเอกสารต้นทางเทียบกับแอป Flutter เวอร์ชันปัจจุบัน รักษาพฤติกรรมที่ตรงตามข้อกำหนดอยู่แล้ว พัฒนาเฉพาะส่วนที่ตรวจพบว่ายังขาด และทำ UAT บนเครื่องจริงโดยมีหลักฐานรองรับ

## ขอบเขตและหลักการ

- ตรวจครบทุก requirement ตั้งแต่ระดับ High ถึง Low-Medium
- คงหน้าจอเลือกกิจกรรมแบบภาพประกอบในปัจจุบัน และไม่ redesign ส่วนที่ไม่เกี่ยวข้อง
- ทำให้หน้าสำหรับเกษตรกรเรียบง่าย ขณะเดียวกันยังเก็บข้อมูลเชิงเทคนิคไว้สำหรับเจ้าหน้าที่และการ export เพื่องานวิจัย
- รักษางานเดิมที่ยังไม่ได้ commit และพัฒนาต่อยอดโดยไม่ย้อนการแก้ไขที่ไม่เกี่ยวข้อง
- รองรับเฉพาะแนวตั้งบนโทรศัพท์และ tablet ทั้ง iOS และ Android โดยปิดแนวนอนที่ระดับระบบปฏิบัติการ
- แยกหลักฐานจาก automated test, การตรวจ layout บน simulator/tablet และ UAT เครื่องจริงออกจากกัน
- หากติดข้อจำกัดจาก hardware หรือ automation ให้รายงานเป็น blocker และไม่ถือว่าการตรวจแบบ manual ที่ยังไม่เสร็จเป็นผลผ่าน

## สถาปัตยกรรม

คงสถาปัตยกรรม Flutter แบบ offline-first ที่ใช้อยู่ในปัจจุบัน การแก้ requirement จะอยู่ภายในขอบเขตของ state, model, service, screen และ widget เดิม การเปลี่ยนแปลงข้อมูลถาวรจะใช้ state ที่จัดเก็บผ่าน `SharedPreferences` และ local image store ที่มีอยู่ ส่วนข้อมูลสำหรับงานวิจัยยังคงผ่าน export service เดิม

ชั้นการตรวจสอบประกอบด้วย unit/widget regression test เฉพาะจุด, integration test ที่มีอยู่, การตรวจ responsive layout, platform build และ UAT บนเครื่องจริง โดยจะมี requirement matrix เชื่อม requirement แต่ละข้อกับโค้ด หลักฐาน automated test และหลักฐานจากเครื่องจริง

## การครอบคลุม Requirement

### 1. ความถูกต้องของข้อมูลและความต่อเนื่องของการประเมิน

- ผู้ใช้สามารถย้อนกลับหรือเปลี่ยนกิจกรรมก่อนบันทึกผลสุดท้ายได้
- เมื่อเปลี่ยนกิจกรรมหลังมีข้อมูลการประเมินแล้ว ระบบต้องเตือนว่าข้อมูลปัจจุบันจะถูกล้างหรือเก็บเป็นฉบับร่าง
- บันทึก draft หลังการเปลี่ยนแปลงข้อมูลสำคัญ และกู้คืน draft ล่าสุดที่ตรงกันหลังเปิดแอปใหม่
- แยก draft ตาม profile เกษตรกร กิจกรรม และวันที่ประเมิน
- ย้ายไฟล์ภาพของ draft ไปยังพื้นที่จัดเก็บถาวรของแอป เพื่อไม่ให้ path ชั่วคราวจากตัวเลือกรูปหายหลังเปิดแอปใหม่
- ปุ่มประเมินผลขั้นสุดท้ายต้องมองเห็นและกดได้บนโทรศัพท์และ tablet ในแนวตั้ง
- ผูกรูปเกษตรกรกับ profile ID และแสดง avatar เริ่มต้นที่คงที่เมื่อไม่มีรูป

### 2. การเลือกรูปและการตรวจสอบรูป

- เลือกรูปได้พร้อมกันสูงสุดสี่รูปจากการเปิดตัวเลือกรูปหนึ่งครั้ง
- แสดง preview สี่ช่องอย่างอิสระ และเปลี่ยนหรือลบแต่ละช่องได้
- ตรวจสอบความเหมาะสมของแต่ละรูปแยกกันก่อนประเมิน
- ปฏิเสธหรือทำเครื่องหมายรูปที่มีหลายคน มี landmark ไม่เพียงพอ หรือคุณภาพไม่เหมาะต่อการใช้งานอย่างชัดเจน
- เก็บผล landmark และ posture เชิงเทคนิคไว้ใน record และ export

### 3. การแสดงผลสำหรับเกษตรกร เจ้าหน้าที่ และงานวิจัย

- หน้าสำหรับเกษตรกรแสดงระดับความเสี่ยง คำอธิบาย body part แบบสั้น Body Map และคำแนะนำที่นำไปปฏิบัติได้เป็นข้อมูลหลัก
- ค่าองศา REBA, ISO 11228, worst posture และรายละเอียด landmark อยู่ในส่วนขยายรายละเอียดหรือหน้าสำหรับเจ้าหน้าที่
- ข้อมูลเชิงเทคนิคยังต้องถูกบันทึกและ export ได้ แม้ไม่แสดงในสรุปหลักของเกษตรกร
- หน้าสำคัญใช้ปุ่ม TTS ที่มองเห็นง่ายและมีรูปแบบสม่ำเสมอ พร้อมข้อความเสียงภาษาไทยที่สั้นและตรงกับ action
- คำถามการประเมินที่มีรายละเอียดมากแบ่งเป็นส่วนสั้น ๆ ใช้ icon และมีระยะห่างที่อ่านง่าย

### 4. คำแนะนำและหน้าสรุปสุดท้าย

- แบ่งคำแนะนำเป็นหมวดท่าทาง การลดความเสี่ยง การพักหรือสลับงาน และอุปกรณ์หรือวิธีทำงาน
- สร้างคำแนะนำจากกิจกรรมจริงและ body part ที่ตรวจพบว่ามีความเสี่ยง
- หน้าสรุปสุดท้ายยังแสดงผลกระทบทางเศรษฐกิจ พร้อม body part ที่มีความเสี่ยงสูงสุดและแนวทางแก้ที่เฉพาะเจาะจง
- หลีกเลี่ยงการแสดงเกณฑ์ท่าทางทั่วไปที่ไม่สัมพันธ์กับกิจกรรมที่ประเมิน

### 5. คู่มือและ UI เลือกกิจกรรมเดิม

- คง UI เลือกกิจกรรมแบบภาพประกอบ ป้ายกำกับภาษาไทย และปุ่มเสียงที่มีอยู่
- ตรวจสอบว่าคู่มือที่รวมอยู่ในแอปใช้ screenshot จริง มีคำอธิบายสั้น มีจุดเน้นที่มองเห็นได้ และเรียงตามขั้นตอนใช้งานจริง
- เปลี่ยนหรือปรับหน้าคู่มือเฉพาะกรณีที่ screenshot ปัจจุบันไม่ตรงกับแอปแล้ว

### 6. แนวโน้ม การ Export การสำรองข้อมูล และ Migration

- หน้าดูแนวโน้มต้องเรียบง่าย มี filter เกษตรกร กิจกรรม และเดือนที่ชัดเจน โดยไม่ใช้ visual ที่ซับซ้อนเกินไป
- รองรับการ export โดยกรองตามเดือนและกิจกรรม
- ทุก assessment ที่ export ต้องมี Farmer ID, ชื่อเกษตรกร, วันที่ประเมิน, กิจกรรม, คะแนนความเสี่ยง, body part ที่มีความเสี่ยง, ข้อมูลอ้างอิงรูปภาพ, ผลวิเคราะห์ AI และเวอร์ชันแอป
- รักษาข้อมูล REBA/ISO/landmark ทั้ง raw และ derived ที่นักวิจัยต้องใช้
- สำรองข้อมูลถาวรก่อน schema migration และย้าย profile, draft และ history จากเวอร์ชันเดิมโดยไม่ให้ข้อมูลสูญหาย
- ตรวจสอบว่า fixture ข้อมูลเวอร์ชันเดิมยังเปิดอ่านและ export ได้หลัง migration

## การไหลของข้อมูล

1. เกษตรกรที่กำลังใช้งานเลือกกิจกรรมและเริ่มการประเมิน
2. การเปลี่ยนแปลงข้อมูลสำคัญแต่ละครั้งจะอัปเดต draft ที่แยกตามเกษตรกร กิจกรรม และวันที่
3. รูปที่เลือกจะถูกคัดลอกไปยังพื้นที่จัดเก็บถาวร และตรวจสอบแยกตามช่อง
4. รูปที่ผ่านการตรวจจะถูกส่งต่อไปยัง pose estimation และการคำนวณ ergonomic risk
5. หน้าสำหรับเกษตรกรแสดงความเสี่ยงและคำแนะนำแบบง่าย ส่วนรายละเอียดที่ขยายได้จะแสดงผลเชิงเทคนิค
6. เมื่อบันทึกผลสุดท้าย ระบบจะสร้าง history record ที่มีเวอร์ชันแอป และลบเฉพาะ draft ที่ทำเสร็จแล้ว
7. Trend และ export service จะกรอง history ที่บันทึกไว้โดยไม่แก้ไขข้อมูลต้นฉบับ
8. เมื่อ schema เปลี่ยนเวอร์ชัน ระบบจะสร้าง backup ก่อนนำข้อมูลที่ migration แล้วมาใช้แทนข้อมูลปัจจุบัน

## การจัดการข้อผิดพลาด

- หากบันทึกข้อมูลไม่สำเร็จ ให้คง assessment ในหน่วยความจำและแสดงข้อความที่ผู้ใช้สามารถแก้ไขหรือลองใหม่ได้
- รูปที่ใช้ไม่ได้ต้องระบุช่องที่มีปัญหาและอธิบายว่าต้องเปลี่ยนรูปอย่างไร
- หากมีข้อมูลการประเมินแล้ว การเปลี่ยนกิจกรรมต้องได้รับการยืนยันอย่างชัดเจน
- หากข้อมูลจำเป็นไม่ครบ ให้ป้องกันการคำนวณขั้นสุดท้ายโดยไม่ลบข้อมูลที่กรอกไว้
- หาก export หรือ share ไม่สำเร็จ ให้แสดงข้อผิดพลาดที่ลองใหม่ได้ และไม่แก้ไข history
- หาก migration ไม่สำเร็จ ต้องกลับไปใช้ข้อมูลหรือ backup ที่เก็บไว้ และห้าม reset ข้อมูลผู้ใช้โดยไม่แจ้งให้ทราบ

## กลยุทธ์การทดสอบ

### Automated Test

- เริ่มจาก baseline ปัจจุบัน: analyzer ผ่าน และ automated test ผ่าน 97 tests
- เพิ่ม regression test ที่ล้มเหลวก่อนการเปลี่ยน behavior แต่ละรายการที่ยืนยันว่าจำเป็นต้องแก้
- ครอบคลุมการแยก draft และกู้คืน media, การยืนยันเมื่อเปลี่ยนกิจกรรม, การแทนที่รูปหลายช่อง, การแจ้งรูปที่ไม่ผ่านแยกตามช่อง, การแยก avatar ระหว่าง profile, metadata ใน export, migration, การแยกข้อมูล farmer/admin และปุ่ม final action บน responsive layout
- รัน analyzer และ test suite ทั้งหมดอีกครั้งหลัง focused test ผ่าน

### Layout และ Build

- ตรวจขนาดหน้าจอโทรศัพท์และ iPad/tablet ในแนวตั้งผ่าน widget/integration coverage
- ตรวจ configuration ของ iOS และ Android ว่าอนุญาตเฉพาะแนวตั้งและไม่หมุนแอปเป็นแนวนอน
- Build artifact ของ Android และ iOS ด้วย toolchain ของโครงการ
- ผล compile ผ่านถือเป็นหลักฐาน build เท่านั้น ไม่ถือเป็น functional UAT

### UAT บนเครื่องจริง

ทดสอบบนอุปกรณ์จริงที่รองรับและเชื่อมต่ออยู่ทุกเครื่อง โดยให้ความสำคัญกับโทรศัพท์ Android อย่างน้อยหนึ่งเครื่อง และ iPhone หรือ iPad อย่างน้อยหนึ่งเครื่องเมื่อมีอุปกรณ์พร้อม:

1. ติดตั้งและเปิดแอป build ปัจจุบัน
2. หมุนอุปกรณ์ไปทั้งสองด้านและตรวจว่าแอปยังคงแสดงผลในแนวตั้ง
3. สร้างหรือสลับเกษตรกรอย่างน้อยสอง profile และตรวจว่า avatar ไม่ปะปนกัน
4. เริ่มประเมิน กรอกข้อมูล ปิดและเปิดแอปใหม่ แล้วกลับมาทำ draft ที่ถูกต้องต่อ
5. เปลี่ยนกิจกรรมระหว่างประเมิน และตรวจข้อความเตือนกับผลการเลือกว่าจะล้างหรือเก็บ draft
6. เลือกสี่รูปพร้อมกัน เปลี่ยนหนึ่งรูป ลบหนึ่งรูป และตรวจ preview แต่ละช่อง
7. ลองใช้รูปที่ไม่เหมาะสมหรือมีหลายคน และตรวจว่าระบบปฏิเสธพร้อมวิธีแก้ที่ชัดเจน
8. ทำ assessment จนจบ และตรวจว่าปุ่มขั้นสุดท้ายกดได้โดยไม่ถูก UI บัง
9. ตรวจสรุปแบบง่าย รายละเอียดเชิงเทคนิคที่ขยายได้ Body Map และคำแนะนำตามความเสี่ยงจริง
10. ฟัง TTS ภาษาไทยในหน้าสำคัญ และยืนยันว่าเสียงสั้น กระชับ และเข้าใจได้
11. กรอง trend/history และ export ตามเดือนหรือกิจกรรม แล้วตรวจ metadata ที่กำหนด
12. เปิดแอปใหม่ขณะ offline และตรวจว่า record, draft, รูป และ flow การประเมินยังใช้งานได้
13. เก็บ screenshot, log, ตัวอย่างไฟล์ export, เวอร์ชันอุปกรณ์และ build รวมถึงผลผ่าน ไม่ผ่าน และ blocker ลงในรายงาน UAT ที่ระบุวันที่

การตรวจที่ต้องพึ่ง hardware เช่น คุณภาพเสียงที่ได้ยินจริง permission dialog, กล้อง และ share sheet ต้องมีหลักฐานจากการสังเกตบนเครื่องจริง หาก automation ไม่สามารถตรวจได้ ให้ระบุ `PENDING-MANUAL` และไม่ถือเป็น `PASS`

## เกณฑ์การยอมรับงาน

- Requirement ทุกข้อมีแถวใน matrix พร้อมสถานะและหลักฐาน
- ไม่มี requirement gap ที่ยืนยันแล้วค้างอยู่โดยไม่มี implementation หรือ external blocker ที่บันทึกไว้
- Static analysis ไม่พบปัญหา และ automated test ทั้งหมดผ่าน
- แอปยังคงอยู่ในแนวตั้งบนโทรศัพท์และ tablet ทั้ง iOS และ Android เมื่อหมุนเครื่อง
- การตรวจ build Android และ iOS เสร็จสมบูรณ์ตาม toolchain ที่มี
- มีการพยายามทำ UAT บนอุปกรณ์จริงที่รองรับและเชื่อมต่ออยู่ทุกเครื่อง พร้อมรายงานหลักฐานที่ระบุวันที่
- รายงานสุดท้ายแยกสถานะ `PASS`, `FAIL`, `BLOCKED`, `NOT AVAILABLE` และ `PENDING-MANUAL` อย่างถูกต้อง

## สิ่งที่อยู่นอกขอบเขต

- การเปลี่ยนหน้าจอเลือกกิจกรรมแบบภาพประกอบที่มีอยู่
- การเพิ่ม cloud synchronization หรือ backend ใหม่
- การเปลี่ยนสูตร REBA/ISO ที่ผ่านการตรวจสอบแล้ว เว้นแต่ requirement gap แสดงให้เห็นว่าสูตรมีข้อผิดพลาด
- การส่งขึ้น Store, production deployment หรือการ reset ข้อมูลเดิมของผู้ใช้แบบทำลายข้อมูล
